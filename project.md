# UELT Web — проєктний документ

> Спільний переклад ігрових локалізацій (`.locres` Unreal Engine та `.csv`) з акаунтами, ролями, статусами рядків і прогресом у реальному часі.
>
> Документ складено за скануванням репозиторію `pasherlife/uelt` (коміт `d949f70`, «First upload») і описує **поточний стан** та **план змін**: нова рольова модель, завантаження файлів у проєкт як `.locres` і `.csv`, експорт і імпорт перекладу в обох форматах.
>
> Позначки: ✅ вже є в коді · 🆕 потрібно додати · ✏️ потрібно змінити.

## 1. Короткий опис

| | |
|---|---|

### 2.1. Модель даних (SQLite)

`users` · `sessions` · `settings` · `projects` · `project_members(can_approve)` · `files(meta JSON, version, rev, struct_rev)` · `file_access(file_id, user_id)` · `rows` · `edits` (журнал правок).

Ключове:
- Рядок ідентифікується як `Namespace::Key`, дублікати отримують суфікс `[n]` (`assignRowIds`).
- Статуси: `0` — без статусу, `1` — на вичитку, `2` — затверджено.
- `rows.ver` — оптимістичне блокування (409 при конфлікті), `rows.rev`/`files.rev` — для поллінгу змін.
- Усі зміни перекладу пишуться в `edits`.

### 2.2. Поточна рольова модель (✅ є, буде замінена)

| Сутність | Як працює зараз |
|---|---|
| Адмін | `users.is_admin`. Перший зареєстрований стає адміном. Бачить усе, керує всім. `requireAdmin()` стоїть на 19 маршрутах (`routes_admin` 8, `routes_projects` 7, `routes_files` 4). |
| Учасник проєкту | `project_members`; бачить усі файли проєкту, редагує **лише файли з галочкою** (`file_access`). |

## 3. Рольова модель (✏️ нова)

### 3.1. Ролі

Дві області: **портал** (глобально) і **проєкт** (локально).

| Роль | Область | Суть |
|---|---|---|
| **Власник** (`owner`) | портал | Єдиний, повний доступ до всього порталу. Не може бути видалений/понижений іншим. Може передати власність. |
| **Адмін** (`admin`) | портал | Створює проєкти та керує ними (учасники, файли, архів, видалення). Бачить усі проєкти. |
| **Менеджер** (`manager`) | проєкт | Керує призначеним проєктом: учасники й ролі, доступ до файлів, завантаження/оновлення/експорт файлів. Не створює і не видаляє проєкти. |
| **Перекладач** (`translator`) | проєкт | Перекладає у **призначених** файлах (як зараз — галочки `file_access`). Результат → «На вичитку». |
| **Редактор** (`editor`) | проєкт | Правит переклад у **будь-яких** файлах проєкту (включно з чужими). Не затверджує. |
| **Рецензент** (`reviewer`) | проєкт | Затверджує рядки / повертає на вичитку, може вносити виправлення в усіх файлах проєкту. |
| **Спостерігач** (`observer`) | проєкт | Лише перегляд: файли, рядки, статистика, прогрес. |

Рядові користувачі порталу мають `users.role = 'user'` і отримують можливості лише через членство в проєктах.

### 3.3. Реалізація

**Схема (міграція «на льоту» в `openDb`, як уже зроблено для `struct_rev`):**

```sql
ALTER TABLE users            ADD COLUMN role TEXT NOT NULL DEFAULT 'user';   -- owner | admin | user
ALTER TABLE project_members  ADD COLUMN role TEXT NOT NULL DEFAULT 'translator';
-- manager | translator | editor | reviewer | observer
```

**Міграція даних (одноразово, ідемпотентно):**

| Було | Стає |
|---|---|
| Найстаріший `is_admin = 1` (мінімальний `id`) | `users.role = 'owner'` |
| Інші `is_admin = 1` | `users.role = 'admin'` |
| Решта | `users.role = 'user'` |
| `project_members.can_approve = 1` | `role = 'reviewer'` |
| `project_members.can_approve = 0` | `role = 'translator'` |

Стовпці `users.is_admin` і `project_members.can_approve` **не видаляти** у першому релізі (відкат, зворотна сумісність); синхронізувати або ігнорувати, а прибрати в наступному релізі.

**`src/perm.js` — замінити `requireAdmin` на здатності (capabilities):**

```js
// одна точка правди; маршрути викликають can(), а не перевіряють ролі напряму
can(ctx, 'project.create')            // owner, admin
can(ctx, 'project.manage', pid)       // owner, admin
can(ctx, 'members.manage', pid)       // owner, admin, manager
can(ctx, 'file.upload', pid)          // owner, admin, manager
can(ctx, 'file.export', fileId)       // owner, admin, manager
can(ctx, 'file.import', fileId)       // owner, admin, manager, reviewer, editor, translator(П)
can(ctx, 'row.edit', fileId)          // …, translator лише з file_access
can(ctx, 'row.approve', fileId)       // owner, admin, manager, reviewer
```

`fileAccess()` повертає `{canView, canEdit, canApprove, canImport, canExport, canManage, role}`; `projectAccess()` повертає ефективну роль (власник/адмін → «всі проєкти», решта — з `project_members`).

**Інтерфейс:** вибір ролі в таблиці учасників проєкту (замість чекбокса «Може затверджувати»), бейдж ролі біля ніка, приховування недоступних кнопок (сервер усе одно перевіряє кожен запит). У вкладці «Користувачі» — колонка «Роль порталу» (лише власник змінює admin/user).

## 4. Файли проєкту: формати

Файл проєкту — це набір **рядків** (`rows`) з оригіналом і перекладом. Джерелом може бути `.locres` або `.csv`.

### 4.1. Завантаження в проєкт (🆕 `.csv`, ✅ `.locres`)

Хто: `owner`, `admin`, `manager`. Один endpoint, формат визначається за розширенням (регістр не важливий):

`POST /api/projects/:id/files?name=<шлях>.locres|.csv[&cv2=…][&delimiter=auto|,|;|tab|pipe]`

Тіло — **сирі байти** файлу (як зараз для `.locres`), ліміт 256 МБ для `.locres`, 50 МБ для `.csv`.

Зміни:
- ✏️ `sanitizeFileName`: дозволити `.locres` і `.csv`.
- 🆕 `files.format TEXT NOT NULL DEFAULT 'locres'` (`locres` | `csv`) — міграція «на льоту».
- 🆕 `importCsvSource(db, {...})` у `importer.js`: створює `files` + `rows` із CSV.
- UI: зона завантаження приймає `.locres,.csv`; вибір набору CV2 застосовується лише до `.locres`.

**Формат CSV-файлу як джерела (оригінал + опційно переклад):**

| Стовпець | Обов'язковий | Синоніми заголовка | Зміст |
|---|:-:|---|---|
| `key` | так | `id`, `rowkey`, `ключ`, `ключрядка` | ID рядка `Namespace::Key` |
| `source` | так | `original`, `text`, `оригінал`, `текст`, `джерело` | Оригінальний текст |
| `translation` | ні | `translated`, `переклад` | Готовий переклад |
| `status` | ні | `статус` | `0/1/2` або `none/review/approved` — береться **лише** якщо в користувача є право затверджувати; інакше «На вичитку» для непорожнього перекладу |

Правила розбору:
- Заголовок зіставляється без урахування регістру, пробілів, `_` і `-` (як зараз у `normalize`).
- Порожній `key` → помилка з номером рядка; **дубль** ключа → помилка (як зараз).
- Порожній `source` дозволений (рядок лишається, 0 слів).
- Кількість стовпців у кожному рядку має збігатися із заголовком (як зараз).
- Лапки, `""` всередині поля, переноси рядків у полі — підтримуються (✅ вже є).
- `files.meta` для CSV-файлу: `{ "csv": { "delimiter": ";", "encoding": "utf-8", "columns": ["key","source","translation"] } }`.

**Як ID перетворюється на `ns`/`key` (для майбутнього експорту `.locres`):** розбиття за **першим** `::`; без `::` — порожній простір імен. Суфікс `[n]` (n ≥ 1) вважається маркером дубліката лише тоді, коли в цьому ж файлі вже є рядок із базовим ID без суфікса; інакше це частина ключа. Правило має бути покрите тестами, бо від нього залежить цілісність ключів при круговому проході `locres → csv → locres`.

### 4.2. Автовизначення роздільника CSV (✏️ покращити)

Зараз: рахуються `,` та `;` у першому записі поза лапками; при рівності — кома. Недоліки: не знає `\t` і `|`, помиляється на заголовках з однією колонкою та на коми всередині тексту.

Нова логіка `detectDelimiter(text)`:

1. Кандидати: `,` `;` `\t` `|`.
2. Для кожного кандидата розібрати **до 20 перших записів** (з урахуванням лапок) і порахувати: кількість стовпців у заголовку, чи однакова вона в усіх записах вибірки.
3. Оцінка: (а) заголовок містить **розпізнані назви** стовпців (`key`/`ключ`, `translation`/`переклад`, `source`/`оригінал`) — найсильніший сигнал; (б) стабільна кількість стовпців ≥ 2; (в) більша кількість стовпців.
4. При нічиї пріоритет: `;` → `,` → `\t` → `|` (`;` — типовий для Excel з українською локаллю).
5. Якщо жоден кандидат не дає ≥ 2 стовпців → помилка «Не вдалося визначити роздільник».
6. Результат повертається клієнту (`delimiter: 'comma'|'semicolon'|'tab'|'pipe'`) і показується в попередньому перегляді; 🆕 параметр `delimiter` дозволяє **вручну перевизначити** автовиявлення.

**Кодування (🆕):** файл приходить як байти; сервер визначає: BOM UTF-8 → UTF-8; BOM UTF-16 LE/BE (Excel «Юнікод-текст», зазвичай з табуляцією) → UTF-16; без BOM — строгий UTF-8, інакше fallback **windows-1251** (типовий експорт Excel в українській локалі). Клієнт більше не читає файл як `file.text()` і не шле його в JSON-рядку — шле сирі байти.

### 4.3. Скачування файлу проєкту (🆕 `.csv`, ✏️ `.locres`)

Хто: `owner`, `admin`, `manager`.

`GET /api/files/:id/export?format=locres|csv`

| Параметр | Значення | За замовчуванням |
|---|---|---|
| `format` | `locres` \| `csv` | формат файлу-джерела |
| `scope` (лише csv) | `all` \| `untranslated` \| `review` \| `approved` \| `notapproved` \| `changed` (ті самі фільтри, що в редакторі) | `all` |
| `delimiter` (лише csv) | `comma` \| `semicolon` \| `tab` | `semicolon` |
| `bom` (лише csv) | `1` \| `0` | `1` (Excel коректно відкриває UTF-8) |
| `version` (лише locres із CSV-джерела) | `0`, `1`, `2` | `2` (Optimized) |

**`.locres` (✅ є, ✏️ узагальнити):**
- Для файлу з `.locres`-джерела — як зараз: порожній переклад → береться оригінал, порядок/хеші збережено, для CV2 — повторне шифрування.
- 🆕 Для файлу з `.csv`-джерела: `ns`/`key` виводяться з ID (§4.1), хеші обчислюються (`strCrc32` для простору імен, ключа і значення), версія — за параметром. CityHash64-версії (3, 4) для CSV-джерела **не підтримуються** (CityHash64 не реалізовано) — повертати зрозумілу помилку.

**`.csv` (🆕):** стовпці `key,source,translation,status`; кодування UTF-8 (з BOM за замовчуванням); текст зі службовими маркерами (`<lf>`, `<cr>`, `<cf>`, `<tb>`) виводиться **як є**, щоб файл імпортувався назад без втрат. Ім'я файлу: `<оригінальна-назва>.csv`, `Content-Disposition` через наявний `contentDisposition()`.

Вимога **кругового проходу**: `export csv` → `import csv` без змін має давати **0 застосованих змін**.

### 4.4. Імпорт перекладу (✅ `.locres` і `.csv` є, ✏️ уніфікувати)

Хто: `owner`, `admin`, `manager`, `reviewer`, `editor`; `translator` — лише в призначених файлах; `observer` — ні.

Зараз це два окремі пункти меню в різних місцях (`.locres` — на сторінці проєкту та в редакторі; `.csv` — лише в редакторі). Робимо **один** пункт «Імпортувати переклад…» (і на сторінці проєкту, і в редакторі), що приймає `.locres` і `.csv` та вибирає обробник за розширенням.

| Крок | `.locres` | `.csv` |
|---|---|---|
| Попередній перегляд | ✅ `POST /api/files/:id/translations` (без `apply`) — звіт | ✅ `POST /api/files/:id/csv-preview` — таблиця з діями для кожного рядка |
| Застосування | ✅ `?apply=1&overwrite=0|1&approve=0|1` | ✅ `POST /api/files/:id/csv-import` з `actions` |

Спільні правила (✅ вже реалізовано, зберегти):
- Збіг за ключем `Namespace::Key`; невідомі ключі пропускаються й рахуються у звіті.
- Порожній переклад або рівний оригіналу/поточному — пропускається.
- Нові переклади → «На вичитку»; перезапис наявних — лише явно (`overwrite`/дія `replace`).
- Затверджені рядки змінює лише той, хто має право затверджувати.
- Кожна зміна пишеться в `edits`.
- 🆕 CSV із колонкою `status` — статус береться лише за наявності права затверджувати.
- 🆕 CSV імпортується як **байти** з автовизначенням кодування та роздільника (§4.2) і з можливістю ручного перевизначення роздільника в діалозі.
- 🆕 Імпорт `.csv` у файл із `.locres`-джерела і навпаки — **дозволений** (імпортується лише переклад за ключем; формат джерела на це не впливає).

## 7. Критерії приймання

**Ролі**
- Власник бачить і може все; адмін створює проєкт, додає учасників, завантажує файли; адмін **не** змінює налаштування порталу і не понижує власника.
- Менеджер керує **лише** своїм проєктом і не бачить чужих (404).
- Перекладач редагує лише призначені файли; редактор — усі файли проєкту; рецензент затверджує; спостерігач не може змінити жодного рядка (403 на всі `PATCH/POST`).
- Після міграції існуючі користувачі мають коректні ролі (найстаріший адмін → власник; `can_approve` → рецензент).

**Файли**
- У проєкт завантажуються і `.locres`, і `.csv`; будь-який інший формат дає зрозумілу помилку.
- CSV із роздільником `,` `;` табуляція `|` розпізнається автоматично; CSV у windows-1251 і UTF-16 читається без «кракозябрів».
- Файл проєкту скачується як `.locres` **і** як `.csv`; `locres → csv → import csv` дає 0 змін; `.locres` із CSV-джерела відкривається парсером `parseLocres` без помилок і зберігає всі ключі та переклади.
- Переклад імпортується і з `.locres`, і з `.csv` — і зі сторінки проєкту, і з редактора.

## 10. Безпека

Лишається (✅): scrypt, сесії з хешем токена, HttpOnly + SameSite=Lax cookie, CSRF-заголовок `X-UELT`, обмеження спроб входу, CSP, заборона виходу за межі `public/`, 404 для сторонніх.

Додати (🆕):
- **Усі перевірки прав — на сервері** через `can()`; приховування кнопок у UI — лише зручність.
- **Захист від «ескалації»:** менеджер не призначає `manager`; адмін не чіпає owner/admin; зміну `users.role` на `admin` виконує лише власник.
- **Журнал ролей:** змінa ролі порталу/проєкту й передача власності пишуться в журнал активності (хто, кому, з якої на яку).
- **Завантаження файлів:** ліміти розміру за форматом, перевірка розширення на сервері, ім'я файлу проходить `sanitizeFileName` (без `..`).
- **CSV-ін'єкція формул** (`=`, `+`, `-`, `@` на початку клітинки) при відкритті експорту в Excel: додати в діалог експорту опцію «Безпечний режим для Excel» (екранування апострофом), **вимкнену за замовчуванням**, щоб не ламати круговий прохід; імпорт при цьому знімає початковий `'`, лише якщо опція ввімкнена в тому ж діалозі.
- Передача власності потребує пароля й завершує сесії обох сторін.

## 11. Відкриті питання (потребують рішення замовника)

1. **«Портал» = один екземпляр чи кілька?** План припускає один портал на встановлення. Якщо потрібно кілька незалежних порталів у одній БД (мульти-тенантність з власним власником у кожного) — це окремий, значно більший етап (`portal_id` у всіх таблицях).
2. **Адмін і користувачі:** чи може адмін керувати рядовими користувачами порталу (вимикати, скидати пароль)? У плані — так; обмеження стосуються лише owner/admin.
3. **Хто скачує:** у плані скачувати можуть `owner/admin/manager`. Чи потрібно дозволити рецензенту (наприклад, для перевірки в грі)? Можна винести в налаштування проєкту.
4. **Редактор vs перекладач:** розрізнення зроблено за **областю** (призначені файли / усі файли). Якщо потрібне інше розрізнення (наприклад, редактор не змінює порожні рядки) — уточнити.
5. **Рецензент і правка тексту:** у плані він може правити текст; якщо лише затверджувати/повертати — це спростить матрицю.
6. **Версія `.locres` для CSV-джерела:** за замовчуванням `Optimized` (2). Чи відомо, яку версію очікує ваша гра/рушій?
